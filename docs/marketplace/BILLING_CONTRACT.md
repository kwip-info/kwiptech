# Marketplace billing and delivery contract

Status: configurable development pricing. Paid sales remain disabled until provider configuration and real sandbox UAT are verified and the catalog contains approved available data. There is no automatic purchase, overage opt-in, customer migration, or live charge in installation/test commands.

## Plans and units

The proposed defaults are Free: 1,000 credits per UTC calendar month; Pro: USD $29/month and 100,000 included credits. Each dataset declares a positive integer credits-per-record (default one). A successful bounded result is billed for actual records returned, not the requested page size. Metadata, errors and empty results are free. Pro supports exports; export authorization belongs to its caller and must check `pro_active(account_for(workspace))`.

Overages are off by default. The browser owner must explicitly enable them and choose a positive cap in cents. Proposed overage pricing is $1 per 10,000 credits (0.01 cents per credit), represented as a Stripe decimal unit price. Only locally calculated excess credits are sent to Stripe. Do not give the Stripe metered price another included tier. The UI's estimated charge rounds upward to the next cent for safe cap enforcement; actual invoicing uses Stripe's invoice rounding. Both browser queries and agent requests must use the delivery service; no free raw-data preview bypass is permitted.

Configuration is server-owned through `MARKET_FREE_CREDITS`, `MARKET_PRO_CREDITS`, `MARKET_PRO_MONTHLY_CENTS`, `MARKET_OVERAGE_CENTS_PER_10000`, `MARKET_BILLING_ENABLED`, `MARKET_STRIPE_SECRET_KEY`, `MARKET_STRIPE_WEBHOOK_SECRET`, `MARKET_STRIPE_PRO_PRICE_ID`, `MARKET_STRIPE_OVERAGE_PRICE_ID`, `MARKET_STRIPE_METER_EVENT` (default `kwip_overage_credits`), `MARKET_STRIPE_LIVEMODE`, and `MARKET_ORIGIN`. Monetary settings must not be changed during active billing periods without a versioned pricing migration; individual delivery receipts retain the applied unit rate. No customer-supplied price/customer IDs are accepted.

## Accounting and periods

`deliver(principal, dataset, request_id, request_fingerprint, producer, max_credits=None)` atomically locks the workspace then refreshes/locks the dataset; runs the bounded producer; checks quota, explicit consent and cap; stores a delivery receipt and exact response; and inserts an overage-only outbox row. No Stripe request runs on delivery. Producers must return `records` and may return count/cursor/snapshot metadata. The response adds `usage` with receipt ID, charged credits, overage credits, row count and remaining allowance. Errors roll back everything. A response cannot exceed 1 MiB. Callers must enforce the endpoint's scope and dataset authorization before invoking this function.

Idempotency is permanent per workspace/request ID. A different fingerprint or dataset returns 409. Replays return the original response without another debit, while rechecking dataset/source withdrawal and current key restrictions. Cached raw responses expire after 24 hours; expired IDs return 410, never rerun. Run `purge_delivery_cache --limit 1000` regularly to remove expired raw payloads while retaining the financial receipt and uniqueness tombstone. Source withdrawal can prevent retrieval of already purchased cached records; no automatic credit is invented—operators review remediation. HTTP success does not prove every byte reached a disconnected client; retry the same ID inside the cache window.

Free periods are UTC calendar months. On the first midmonth Pro activation, the allowance window includes usage since the start of that UTC month, avoiding an upgrade reset. Subsequent verified Stripe period changes reset the Pro window at the provider period boundary. Refreshing the same subscription period leaves usage intact. Downgrade uses the current UTC calendar month's existing ledger, rather than issuing a fresh Free allowance. Subscription entitlement expires at its verified period end even if no webhook arrives. A failed/pending/unpaid/canceled state disables paid overage and falls back to Free access; account management remains accessible. Changing plans does not erase usage or cancel already earned charges.

## Stripe operation

Stripe SDK 14.4.1 calls use API version `2026-02-25.clover`, a 10-second HTTP timeout and no SDK automatic retries. Checkout creates a monthly fixed item plus a sum-meter item; the latter has no billable usage until explicit local consent. Configured prices are checked against amount, currency, environment, interval, usage type and meter name. Checkout is blocked server-side while no published, approved-source, non-tombstoned records exist. Portal access remains available for historical/current billing management even if the catalog later empties.

Checkout customer and session calls have stable idempotency keys. A browser return URL is informational. A signed webhook is durably recorded with a unique event ID, then the reconciliation command fetches the current subscription instead of trusting event arrival order. Only the configured items, expected customer/environment, active status and verified paid latest invoice can grant Pro. Canceled or unpaid status revokes overage consent; reactivation requires new opt-in. The new webhook route must remain outside the retired legacy `/webhooks/*` namespace.

`dispatch_usage --limit 100` submits pending events with the delivery UUID as both stable meter identifier and idempotency-key suffix. It leases work, applies bounded retries with jitter, records permanent validation errors for review, and never recreates an old event under a new ID. At 23 hours from an ambiguous first attempt, further automatic retries stop to stay inside Stripe's 24-hour identifier deduplication window. Operators must reconcile the remote result before resolving these events. A successful meter HTTP response records submission, not proof of final billing acceptance.

`reconcile_billing --limit 100` drains signed webhook records, refreshes subscriptions and compares settled local overage totals with Stripe summaries using a 15-minute lag. Durable `MeterReconciliation` records distinguish matched, unsettled and mismatch. It does not synthesize adjustments or charges. Failures return a nonzero command result. Initial implementation refreshes subscriptions serially while holding the workspace control-plane lock to prevent stale in-flight responses overwriting newer state; this can briefly block that workspace's API traffic and should be measured. Introduce a per-account lease/version protocol if this becomes a material latency cost.

Schedule these bounded commands externally; none registers a scheduler or invokes provider APIs during migration. Monitor old pending/failed webhooks, old outbox leases, `review` rows, non-matched reconciliation, and cache purge age. Configure Stripe's meter error notifications operationally; a submission success alone does not establish acceptance. Meter discrepancy resolution, credits/refunds, and historical-period reconciliation remain explicit operator procedures, not automated guesswork.

## Validation and rollout

Unit tests exercise signed webhook verification, duplicate delivery/event behavior, cap/allowance bounds, failed provider calls, stale ambiguity, account isolation, lifecycle states, source withdrawal, raw cache expiry, price refresh and service-key denial on billing controls. A PostgreSQL-specific concurrent-last-credit test verifies the shared lock. These tests mock Stripe network calls and do not replace real sandbox Checkout/Portal/renewal UAT. Keep synthetic records exclusively in an isolated test database; production ends empty and sales disabled. A temporary Stripe sandbox proves integration behavior, not production account readiness.

## Identity revocation and account deletion

`/integrations/clerk` must point to `plane.access.webhooks.clerk_webhook`. Configure a dedicated `MARKET_CLERK_WEBHOOK_SECRET` from that Clerk/Svix endpoint and subscribe to `user.deleted`, `session.ended` and `session.revoked` (the handler also safely recognizes `session.removed` if supplied). The endpoint verifies the exact raw bytes using Svix's documented `message-id.timestamp.body` HMAC-SHA256 construction, base64 secret/signature, constant-time comparison, and a five-minute timestamp bound. Both Svix and standard Webhook header names are accepted. No additional provider SDK is required. Tests cover body tampering, stale/future timestamps, multiple signatures, duplicate events and real RSA token revocation. [Svix verification specification](https://www.svix.com/guides/receiving/receive-webhooks-with-python/)

A signed user deletion creates or updates a permanent inactive identity tombstone, revokes existing service keys, disables paid overage and writes `cancellation_requested_at` on its existing billing account in the same transaction. User-created/updated events never restore that identity; even an accidental active-flag change leaves the deletion tombstone effective. Pending/approved device grants cannot mint new keys for that owner. Session termination revokes that specific JWT session but deliberately leaves independently authorized agent keys intact; deleting the identity revokes both. Financial receipts and minimal revocation/event identifiers remain, with no whole Clerk user payload stored.

`reconcile_billing` processes the durable cancellation request even if a Stripe subscription has not yet been mapped locally. It lists the workspace customer's open subscription Checkouts, expires matching unconsumed sessions, finds nonterminal subscriptions and cancels them. Transient provider failure leaves the request pending for retry; repeat processing is idempotent. The worker records `cancellation_completed_at` only after provider calls succeed. Conflicting ownership metadata or excessive pagination fails closed for operator review. It requests neither an immediate invoice nor prorated charges. Previously earned usage/invoice receipts remain for staff review; deletion does not promise refunds or erase existing obligations. An ambiguous provider cancellation is retried by first reading current status, not assuming the timeout means failure.

Checkout's final creation and local persistence serialize with deletion through the workspace lock. A deleted identity cannot receive a newly usable checkout through a stale browser principal. Billing-management controls must remain visible to a delinquent customer while their account still exists (`billing_account_exists` is independent of `plan`). Overage setting changes also create permanent `BillingConsent` receipts with identity, timestamp, cap and pricing rate.

The current Clerk v2 default claims include `exp`, `iat`, `nbf`, `iss`, `sub` and `sid`, matching server requirements. Browser code must request the default session token via `session.getToken()` rather than a long-lived custom JWT template. The application additionally requires its configured `azp` origin and at most a 120-second token lifetime; Clerk can omit `azp` when Origin is absent, and such tokens are intentionally rejected for this browser-only sign-in path. Nested organization claims are not used as marketplace billing authority. Unknown JWT header fields are tolerated. [Clerk session-token reference](https://clerk.com/docs/guides/sessions/session-tokens)

JWKS verification uses a shared database snapshot (300-second freshness default), a per-issuer 60-second minimum refresh interval and a five-second provider timeout. Keyset downloads are capped at 256 KiB and 64 keys. Failed fetch timestamps survive error responses, so unknown-key spray cannot force an outbound request for every token. All workers use the same snapshot, avoiding independent cold-start throttling. Settings: `MARKET_JWKS_CACHE_SECONDS`, `MARKET_JWKS_REFRESH_SECONDS`, `MARKET_JWKS_TIMEOUT_SECONDS`; static `MARKET_CLERK_PUBLIC_KEY` can instead be configured with an operator-owned rotation process. Pre-authentication attempts also have a shared peer bucket (`MARKET_AUTH_ATTEMPTS_PER_MINUTE`, default 600), followed by JWT and workspace limits.

Operational checks: alert on cancellation requests lacking completion; exercise signed deletion against an isolated sandbox account with a pending Checkout and active subscription; simulate provider failure/retry; confirm old agent keys and unexpired browser JWTs are denied; verify a delayed user-created event cannot restore access; retain provider cancellation receipts in the private deployment record. No actual cancellation, charge, or provider webhook registration occurs in migrations or unit tests.

### Final concurrency review

Delivery refreshes the owning identity and service key after acquiring the workspace lock; revocation uses the same workspace-to-key order. This prevents an expired, revoked or narrowed key captured before a lock wait from retrieving a fresh or cached result. Exports validate source coverage for both the requesting key and original actor, and materialize artifacts while holding current workspace/dataset/source authorization. Export workers acquire workspace before job/dataset locks. A recovered renewal uses its verified new Stripe period even if the previous local status was past due; only initial activation or a new subscription carries earlier calendar-month usage into its allowance.

Worker selection excludes not-yet-due meter retry/lease rows before its batch limit, and excludes completed account-deletion cancellations from the live subscription scan. Regression tests reproduce the prior bypasses and starvation boundaries. The final local PostgreSQL whole-repository run passed 314 tests; this is code-level evidence, distinct from provider sandbox and browser UAT.
